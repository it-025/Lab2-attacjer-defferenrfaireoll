🛡️ Модуль 1: Активное реагирование и сетевой мониторинг (Fail2ban & Suricata)

1. Настройка Fail2ban для защиты SSH

Цель: Автоматическое обнаружение попыток брутфорса и динамическая блокировка атакующих IP-адресов через межсетевой экран[cite: 9].

  • Проблема окружения: В современных сборках Kali Linux системный SSH перешел на использование systemd и сессий sshd-session, что ломает стандартные регулярные выражения фильтров Fail2ban[cite: 9].
  • Решение: Подключена и настроена служба rsyslog для дублирования событий в текстовый лог-файл /var/log/auth.log[cite: 9].
  • Бэкенд опроса: В файле jail.local принудительно задан параметр backend = polling для стабильного мониторинга логов[cite: 9].
# Команды проверки работы Fail2ban
sudo fail2ban-client status sshd
fail2ban-regex /var/log/auth.log /etc/fail2ban/filter.d/sshd.local

Результат: После тестовой атаки утилитой Hydra зафиксировано успешное блокирование хоста (Total banned: 1)[cite: 9].

2. Домашнее задание: Правило обнаружения Suricata для SSH Brute-Force

В рамках домашнего задания разработано кастомное правило для IDS Suricata, размещаемое в файле /local.rules[cite: 9]:

alert tcp any any -> any 22 (msg:"SSH Brute Force Attempt Detected"; flow:established,to_server; threshold: type both, track by_src, count 5, seconds 60; sid:1000001; rev:1;)

Детальный разбор ключевых полей правила и порога срабатывания:

  • flow:established,to_server — анализ уже установленных TCP-соединений, направленных от клиента к SSH-серверу (порт 22), что отсекает пустые сканирования и фиксирует реальные попытки аутентификации.
  • threshold: type both, track by_src, count 5, seconds 60 — механизм контроля порога срабатывания:
    • track by_src — ведение подсчета отдельно для каждого уникального IP-адреса источника.
    • count 5 и seconds 60 — лимит: если с одного IP поступает 5 и более запросов в течение 60 секунд, фиксируется тревожное событие.
    • type both — режим выдачи алертов, фиксирующий превышение лимита без избыточного заспамливания журнала.
  • sid:1000001 — уникальный идентификатор пользовательского правила (Security ID).

⚠️️ Сложности модуля 1 и их преодоление:

Главная сложность заключалась в синтаксических особенностях запуска правил через командную строку терминала (`zsh` выдавал `parse error` из-за круглых скобок и точек с запятой). Проблема решена корректным внесением правил через текстовый редактор `nano` в файл локальных правил Suricata[cite: 9].

🗄️ Модуль 2: Безопасность СУБД, разграничение доступа и аудит (PostgreSQL)

Цель: Развертывание защищенной реляционной СУБД, реализация ролевой модели (ИАФ, УПД), аудит (РСБ), сетевая изоляция и политики безопасности для ИИ[cite: 9].

1. Устранение системного конфликта локали (Collation)

После обновления системных библиотек glibc в Kali Linux возникло несоответствие версий сортировки (2.41 против 2.43), вызывающее ошибки шаблона[cite: 9].

ALTER DATABASE template1 REFRESH COLLATION VERSION;
ALTER DATABASE postgres REFRESH COLLATION VERSION;
CREATE DATABASE aszi;
\c aszi

2. Проектирование реляционной и документной структуры

Созданы таблицы regions, citizens, requests со строгими внешними ключами (`FOREIGN KEY`) и ограничениями целостности[cite: 4], а также таблица documents (jsonb) для полуструктурированных данных[cite: 5].

3. Ролевая модель и проверка отказов (ИАФ + УПД)

Созданы роли op_msk и analyst с минимально необходимыми привилегиями. При попытке оператора выполнить несанкционированное удаление записей (`DELETE FROM requests`) СУБД закономерно выдала отказ permission denied[cite: 6].

4. Журнал аудита (РСБ) и Политика ИИ (Приказ №117)

  • Аудит изменений: С помощью триггера trg_requests и функции log_change() каждое изменение в таблице обращений автоматически фиксируется в журнале audit_log[cite: 7].
  • Защита данных при работе с ИИ: Настроена таблица политик и логов ai_log, где запросы, содержащие персональные данные (например, ФИО «Иванов И.И.»), безусловно блокируются со статусом false[cite: 5, 8].

5. Проверка сетевой изоляции СУБД

С помощью утилит ss -tlnp и nmap 127.0.0.1 подтверждено, что PostgreSQL прослушивает исключительно локальный интерфейс (127.0.0.1:5432), исключая сетевой доступ извне[cite: 5, 8].

Основные трудности были связаны с системными предупреждениями о несовпадении версий локали после обновлений ОС[cite: 9], а также с необходимостью точного предоставления прав на последовательности (sequences) для корректного автоинкремента у непривилегированных пользователей СУБД.
